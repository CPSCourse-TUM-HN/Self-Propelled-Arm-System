# Notebook And Parameter Guide

All active Notebook numeric controls use text-entry widgets (`FloatText` or `IntText`), not sliders.

## Motion Performance

`../tuning_tools/base_motion_performance.ipynb` keeps `base_real` disabled by default. Its shared conversion values are:

- `linear_m/(v*s)`: estimated meters traveled by speed `1.0` for one second.
- `linear_slip`: empirical multiplier for straight-line slip.
- `angular_rad/(v*s)`: estimated radians turned by turn speed `1.0` for one second.
- `pulse_chunk_s`: Stop polling interval; it does not insert repeated motor stops.

The square uses the origin and `(point_x_m, point_y_m)` as adjacent vertices. The remaining vertices are generated by a 90-degree rotation, so the route is a true square even when both coordinates are nonzero. The semicircle is approximated by short chord segments. Fast-slow-fast cruise changes motor speed without intentionally stopping between phases.

The same Notebook also contains a direct timed square: four `linear_speed × linear_seconds` segments with independent `left_speed/left_90_seconds` and `right_speed/right_90_seconds` inputs. These values stay in memory and STOP interrupts the active segment.

All motion-performance command speeds are direct numeric inputs in `(0.0, 1.0]`. Their initial values come from the configured named speed profiles, but changing a field only affects that diagnostic run and does not save parameters.
At speeds present in `base_turn_response.samples`, angle-based motion uses the measured left/right time for a 90-degree (`pi/2` radian) turn. `angular_rad/(v*s)` remains the fallback for an unmeasured speed. Docking and avoidance use the same table when matching an opposite timed turn to an earlier turn angle.

## Obstacle Avoidance Tuning

`../tuning_tools/obstacle_avoidance_tuning.ipynb` reads its own
`obstacle_avoidance_parameters.json` and never writes production empirical parameters.
`perception.obstacle_top_ignore_ratio` excludes the top part of the depth map only
from obstacle-contour extraction. The default is `0.30`. Camera frames, DepthNet input,
background/center depth sampling, HUD rendering, and recordings remain full 320x240.
`perception.obstacle_bottom_ignore_ratio` similarly excludes the bottom floor band;
the default `0.15` leaves the vertical 30%-85% band for obstacle contours.
The most important first-pass values are `perception.relative_depth_drop`,
`perception.center_corridor_width_norm`,
`motion.minimum_offset_seconds`, `motion.maximum_offset_seconds`, and
`motion.pass_min_seconds`. At initial obstacle confirmation, the session freezes the
contour's robust depth proxy (the current implementation uses the median). The first
lateral segment uses `motion.depth_to_segment_time_factor * locked_obstacle_depth`,
and its actual duration is replayed by `OFFSET_RETURN`. The independent second straight
segment uses `motion.pass_depth_to_time_factor * locked_obstacle_depth`. `PASSING`
is a deterministic-length segment: once this target duration is reached, it transitions
to `TURN_TO_LINE` even if the current observation is an ignored wall or still contains
the earlier obstacle. Emergency and absolute close-depth protection remain active.
`control.obstacle_confirmation_frames` controls how many
consecutive stationary observations of the same associated bbox are combined into
the locked obstacle before starting a bypass. During `TURN_TO_TANGENT`, only that
obstacle is tracked across all candidate bboxes. A frame is safe when the locked
bbox is outside the center collision corridor or absent; unrelated bboxes do not
replace it. Frames classified as `IGNORED_WALL` are treated as clear-path samples,
including incrementing the tangent safe streak, while still participating in
absolute-depth protection.
`perception.tracking_max_center_shift_norm`, `tracking_min_area_ratio`,
`tracking_max_area_ratio`, and `tracking_depth_tolerance_ratio` control association.
`control.tangent_safe_frames` is the consecutive safe-frame count required to stop
the turn, so a single missing or outside frame cannot stop it. Stopped verification
passes after `control.post_turn_clear_frames` consecutive clear observations and
fails only after `control.blocked_failure_frames` consecutive blocked observations;
an intervening clear observation resets that failure streak. A persistently blocked
`TURN_PARALLEL` repeats tangent/offset correction up to
`control.maximum_lateral_corrections`, and all outbound segments are replayed in
reverse during route restoration. The old `control.clear_stable_frames` value remains
in the standalone JSON for compatibility but no longer controls these decisions.
`perception.absolute_center_stop_depth`
is the fallback for a close wall that produces no relative contour. Always inspect one
stationary HUD frame before enabling `base_real`.
`perception.wall_width_threshold_norm` defaults to `0.60`. A center-intersecting
bbox at least this wide is logged and drawn as `IGNORED_WALL`, but it does not start
ordinary obstacle avoidance. Absolute center-depth and emergency-depth protection
remain active, so approaching the ignored wall closely still stops the base.
Wide bboxes do not fail with a "no traversable side" gate. The planner always
chooses the side with more visible clearance (or `perception.default_side` for
a near tie), then relies on visual-clear conditions, phase timeouts, and the
absolute/emergency depth limits for safety.
`control.linear_obstacle_confirmation_frames` applies the same stop-and-confirm rule
to `OFFSET_OUT`, `PASSING`, and `OFFSET_RETURN`. A rejected candidate resumes the interrupted motion;
a confirmed candidate starts a nested tangent bypass. If the return segment is
interrupted, its untraveled duration is stored and resumed after the nested bypass.
`Geometry HUD` controls the obstacle mask, reference corridor, ROI boundary, bbox,
and tangent guides. `Text HUD` independently controls the compact state and depth
readout. Detailed side selection, reasons, and motion estimates remain in logs only.

## Camera Interruption

`camera_depthnet_interrupt_test.ipynb` intentionally separates CameraOnly from DepthNet. `STOP + RELEASE CAMERA` calls camera stop and drops the wrapper reference without unloading DepthNet. `Unload DepthNet` removes model references and requests garbage collection. `STOP + RELEASE ALL` performs both operations.

DepthNet and obstacle tools use the shared calibrated frame path when
`camera.depth_rectification_enabled=true` (disabled by default). Can DetectNet remains in raw
image space unless `detectors.can.rectification_enabled=true`. AprilTag detection and
PnP continue to use the raw frame together with its distortion coefficients; do not
pre-rectify AprilTag input.

## Two Active JSON Files

`config.json` contains operational choices: paths, hardware dry-run flags, retry policy, detector enablement, depth enablement, and avoidance strategy.

Mission completion uses `runtime.max_pickups`. The current count is held in memory as `MissionContext.completed_pickups`; it is not an empirical parameter and is reset to zero for a new runtime.

`empirical_parameters.json` contains values learned through testing: named base-speed profiles, pulse durations, timeouts, tolerances, detector thresholds, stop thresholds, ROIs, servo orders, and poses.

Production base-speed settings use `linear.fast`, `linear.slow`, `turn.fast`, or `turn.slow` references according to motion type; their numeric values live under `base_motion_speed_profiles`. The motion-performance diagnostic is the exception: its command fields accept direct numeric test values without saving them. Arm speed remains a numeric servo-controller value.

`base_motion_command_scales.forward/backward/left/right` are empirical command multipliers. All default to `1.0`, so they do not change the current behavior. `BaseController` rejects an effective speed above `1.0` instead of silently clipping it. The base calibration Notebook stores a surface label and reports left/right scale suggestions; it does not call these values friction coefficients.

Saving a notebook itself does not save parameters. Parameters change on disk only when the arm tuning notebook explicitly invokes its save action, or when the JSON file is edited and saved directly.

## Camera And Network Diagnostics

Open `tuning_tools/camera_network_diagnostics.ipynb`. It uses `DemoDiagnostics`; it does not contain a second camera/model implementation.

Recommended order:

1. Reload configuration.
2. Start camera and capture a frame.
3. Load the can detector and test one frame.
4. Load the AprilTag detector and test one frame.
5. Test depth if `camera.depth_enabled` is true.
6. Start the low-rate overlay for visual center/bounding-box checks.
7. Release camera before restarting the kernel or opening another camera notebook.

The reload-model checkbox controls whether the cached detector object is discarded. Leave it off during ordinary tuning to avoid repeated detectNet initialization.

Can model paths, confidence thresholds, and clustering are stored directly under `detectors.can` in `empirical_parameters.json`.

## Full Demo Integration

Open `tests/full_demo_integration_test.ipynb`. It creates the same `DemoStateMachine` used by `run_demo.py`.

- Reload configuration reads both JSON files again and creates a fresh runtime.
- Preflight starts the camera and checks depth/can/tag through `DemoDiagnostics`.
- Step executes one FSM transition for controlled inspection.
- Run executes the complete mission.
- Stop requests a safe stop; Release Camera closes the shared camera path.

Logs are mirrored to a timestamped file under `logs/`. The notebook does not expose sliders and does not write either JSON file.

## Arm Sequence Tuning

Open `tuning_tools/arm_sequence_tuning.ipynb`. It directly reads and writes only the `arm` section of `empirical_parameters.json`.

Pose names:

| Pose | Meaning |
| --- | --- |
| `safe_home` | collision-conscious initial/final pose and camera orientation |
| `arm_down` | lower the claw to pickup height |
| `grab` | close the gripper; all five servo values are explicit |
| `carry` | lift and retain the object for base motion |
| `release` | bin-insert geometry with Servo 4 open; normal and side release share it |
| `side_view_grabbing` | exp2 calibrated right-view pose that keeps the can gripped |
| `side_view_bin_insert` | after visual side-docking correction, extend into the bin while Servo 4 remains closed |

The base push is not an arm pose. It uses `arm.push.speed`, `arm.push.seconds`, and `arm.push.post_lock_seconds`.

Use dry-run first. A Show action reads and executes the saved pose without writing. Apply executes the current in-memory values without writing. Save writes the selected pose to `empirical_parameters.json`; different pose buttons save only their corresponding pose object.

## Focused Hardware Diagnostics

- `tuning_tools/arm_grasp_telemetry_test.ipynb` reads SCSCL position, speed, load, voltage, temperature, moving and current fields. Real arm access and gripper motion require separate explicit checkboxes. CSV output is diagnostic only and does not change pickup decisions.
- `tuning_tools/dual_can_vague_map_recording_test.ipynb` recreates the production carrying condition without real base/arm access. Its primary HUD always follows DetectNet and draws every current can bbox; vague-map acceptance cannot hide a detection. The optional `show_vague_map` checkbox adds the robot/remembered-can inset. Live display is on by default; AVI + synchronized CSV recording is opt-in.
- `tuning_tools/dual_obstacle_detection_test.ipynb` starts Camera + DepthNet without constructing a base controller. It continuously shows every candidate bbox and reports two-candidate, merge, false-split, and cross-frame identity rates. It now uses the same opt-in AVI + synchronized CSV recording controls as the dual-can test.
- `tuning_tools/camera_intrinsic_calibration.ipynb` captures checkerboard views and saves a compatible calibration YAML without editing production configuration.
- `tuning_tools/apriltag_pnp_stability_test.ipynb` requires that YAML and reports translation/orientation statistics. It never substitutes DepthNet when calibration is unavailable.

## Navigation Parameters

Each target has `search`, `align`, `approach`, and optional `near_align` sections under `navigation`.

- Search: `direction`, turn-speed profile, `pulse_seconds`, `timeout_seconds`.
- Align: turn-speed profile, `pulse_seconds`, `tolerance_norm`, `max_steps`, `lost_frame_limit`.
- Approach: forward and steering speeds/pulses, timeout, pulse limits, lost-frame limit, and `stop`.
- Stop mode `bbox_height`: stop when normalized box height is at least `bbox_height_threshold`.
- Stop mode `depth`: stop when the lens-center DepthNet mean is at most `depth_raw_threshold`.
- Stop mode `bbox_height_and_depth`: stop only when both conditions pass in the same frame.
- Near align: a tighter post-approach center check before arm/bin finalization.

`tuning_tools/can_stable_stop.ipynb` tests only the longitudinal stop immediately before
`arm_down`. Real base motion is opt-in. The live HUD and optional recording display both
measurements even when only one controls stopping; physical ideal/measured gaps can be
annotated in the generated CSV. It never runs arm poses or the fixed push action.

Edit the JSON, save it, then reload configuration in the notebook before the next test. Existing in-memory objects do not automatically notice disk changes.

`navigation.can.near_align.required_stable_frames` is the normal pre-pickup visual
confirmation count. Incidental cans observed while carrying use the same can confidence
acceptance rule and half this count (rounded up, minimum one frame). They no longer have
a separate image-height cutoff; valid depth and map bounds are still required.
